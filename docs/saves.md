# Saves

## Where worlds are kept

- **IndexedDB** database `sosaria`, stores `slots` (the world text plus its metadata) and `meta` (metadata only, for fast listing). Small preferences stay in `localStorage`: `sosaria-quality`, `sosaria-settings`, and `sosaria-observer` (favourites, recent places and pinned Chronicle threads per seed).
- **Manual slots** (`manual-…`), **three rotating autosaves** (`auto-1`…`auto-3`; the oldest is replaced every minute of play and when the tab is hidden), **experiment branches** (`branch-…`), and `migrated-v1` for a migrated 0.1 world.
- **Export** downloads a JSON file `{ format: "sosaria-world", manifest, state }`. It is the portable backup: browsers may evict site storage, and IndexedDB is not a promise of permanence.

## Writing safely

1. The world is serialized, parsed back and fully validated (see below) before anything is written.
2. One IndexedDB transaction moves the slot's current snapshot to `<slot>~previous` and writes the new one. If the transaction fails, nothing changes.
3. A slot that holds a newer schema is never overwritten.
4. Each slot has a revision. A tab that loaded revision *n* refuses to save over a revision another tab has since written ("conflict"). It can save to a new slot instead.
5. A second tab on the same world is read-only: the Web Locks API holds `sosaria-world`, with a BroadcastChannel probe where locks are unavailable. It can explore and export, but not save.
6. After a simulation error the app stops saving, so the last valid save is untouched.
7. Storage errors are explained: a full disk ("Browser storage is full. Export this world to keep it, or delete old saves"), storage unavailable (saves then last only until the tab closes), or an interrupted write.

Loading a slot whose latest snapshot is unreadable falls back to `<slot>~previous` and says so.

## Validation

`validateState` (`src/sim/snapshot.js`) checks, before a world replaces the running one:

- Size: 16 MB at most. Nesting depth, list lengths and string lengths are bounded. No `__proto__`, `prototype` or `constructor` keys, and only finite numbers.
- Schema version 2, a matching catalog signature, the header, allocators and random stream states.
- Every settlement exists and has valid resources. Households and residents reference each other and real homes and graph nodes. Needs are in range. Journeys and jobs exist.
- Inventories hold only known goods in positive integers, with reservations never above stock.
- Buildings, fields, jobs, shipments, contracts, incidents and closures reference catalog entities and real routes.
- History IDs strictly increase, were issued by the allocator, and are never later than the world tick; the due-work queue is well formed.
- No negative stock, and the resource ledger balances exactly for every good.

Imported names are data. The interface escapes all text when rendering.

## Format and versions

| Field | Meaning |
| --- | --- |
| `schemaVersion` | 2 in 0.2.0. Newer is refused and left untouched; 1 is migrated. |
| `contentVersion`, `generationVersion`, `scenario` | `0.2.0`, `1`, `sosaria-default` |
| `catalog` | signature of the derived world: places, buildings, walkable graphs and travel edges |
| `migratedFrom`, `branch`, `interventions` | provenance: a migration, an experiment's origin, recorded rule changes and experiments |

Derived data is never saved: meshes, terrain, walkable graphs and distance caches are rebuilt on load. Sub-tick interpolation is not saved either; a reloaded world resumes on its exact tick.

## Migrating 0.1 worlds (schema 1)

The first living-world release stored one world in `localStorage` (`sosaria-world-v1`, with `-previous`), counted one tick per world second, and had a six-person named cast per town. On first start, 0.2.0 migrates such a world once into the `migrated-v1` slot and leaves the original keys untouched. The migration:

- proves the save belongs to this world with the schema 1 layout signature (`src/sim/legacy.js`);
- converts time (a world second becomes 1,440 ÷ 420 minutes) and starts the new world at that minute, without simulating the gap;
- keeps the seed, every history entry (as `legacy` records with their causes), the named cast (same IDs, names and roles, with their memories), each town's knowledge, damaged buildings (now with repair projects), and active road closures;
- rebases settlement stocks onto the schema 2 scenario and completes journeys that were in progress, and records both in a `migration` event.

The fixture `tests/fixtures/save-v1-default.json` was generated by the 0.1 code at world second 300 of the default seed (schema 1 counted seconds), while the introductory fire's damage awaited repair. The migration test checks it.
